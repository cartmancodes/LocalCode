# Rust terminal UI implementation — 2026-10-03

The optimized `target/release/octet` executable now opens a real terminal
interface. This implements an interactive vertical slice of the approved design;
it does not replace the existing application or complete the parity matrix.

## Delivered

- Ratatui/Crossterm interface with graphite/mint styling, responsive workspace
  panel, streaming conversation, multiline composer, word wrapping, prompt
  history, scrollback, command palette, help and an approval overlay.
- `octet-engine::live`: persistent Codex and Claude subprocess drivers, correlated
  turns, approval deadlines, explicit denials, independent cancellation/shutdown
  signals, streamed text/tool events, vendor session resume and usage display.
- `octet-core`: presentation-independent session boundary, bounded event delivery,
  journal-before-display ordering, storage failure handling and safe export.
- `octet-store`: exclusive 0600 preview journals, sequence numbers, size quota and
  completed-turn synchronization. Existing pi v3/legacy files are untouched.
- `octet`: composition root with explicit engine, workspace, model, binary,
  resume and journal-directory options; offline demo needs no vendor CLI.
- Terminal restoration on ordinary exit, SIGTERM/SIGHUP, panic and suspension.
  Escape sequences split across model chunks are removed before rendering.
- `make tui`, `make tui-demo`, `make rust-build`, and documented user installation.

## Verification

- 36 offline Rust tests pass on macOS ARM64 and Linux ARM64 (Docker with `--init`).
  Two performance diagnostics are opt-in rather than normal correctness tests.
- Real PTY tests exercise Unicode bracketed paste, a multi-line prompt, approval
  denial, resize, suspend/continue, Ctrl+Q, SIGTERM during streaming and restoration
  of the original terminal flags. These tests use Rust/libc only.
- Deterministic vendor subprocess tests cover repeated turns, Claude stream/final
  deduplication, Codex intermediate message vs. terminal completion, late usage,
  cross-thread isolation, approval responses, stale answers and interruption.
- Clippy with warnings denied, rustfmt check and repository-wide Ruff pass.
- Live Codex 0.154.0 in a temporary workspace completed a prompt through the actual
  TUI. The journal contains one READY text event, usage and a completed terminal
  outcome; Ctrl+Q restored the terminal and stopped the owned child.
- Claude live authentication was previously expired and remains a verification
  limitation. Offline adapter tests do not establish current vendor login health.
- Single optimized macOS demo diagnostic: approximately 552 ms to the journaled
  ready event, 3,856 KiB RSS, zero repaint output during five idle seconds, with
  reported cumulative CPU unchanged at 0.01 s. Cache state was not controlled;
  this is not a p95 benchmark or proof of the 60-second CPU release requirement.
- The optimized macOS executable is approximately 2.2 MiB. Linux binaries must be
  built on Linux; no static/musl or x86-64 release claim is made.

## Issues caught during terminal testing

Ratatui's public `clear()` queries the cursor position, conflicting with the
active input reader and failing in a PTY without a cursor response. Fullscreen
resize invalidation now clears without a cursor query. The default terminal input backend also
exhibited intermittent wakeup loss around simultaneous Linux resize/key events.
The `use-dev-tty` backend uses level-triggered polling instead. A dedicated thread
owns poll/read and forwards through a bounded channel, without an idle render
timer. These paths are covered by the real PTY test. The test reads terminal
attributes from the PTY master, which remains valid after the child releases its
controlling terminal.

Oversized approval requests are denied rather than presenting a truncated request
with an allow button. Full tool events are split into bounded chunks before
journaling. Display retention limits do not truncate the journal; overload or
storage exhaustion explicitly stops the session.

## Remaining migration work

See [the TUI guide](../tui.md) for the exact supported surface and
[the parity matrix](../rust/parity-matrix.md) for release requirements. In
particular, v3 recovery/browsing, fleet, plugins/resources, images, queues and
legacy-compatible RPC/print/JSON remain pending. Vendor-context resume is supported;
local transcript replay is not. Pending features are not represented as working
commands or passing acceptance tests. The earlier application remains available.
